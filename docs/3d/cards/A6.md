# A6 流式接口：实时版的智多星在想（第三批）

**做完的样子**：和 A5 看起来一样，但每一步都是真的、而且更早：模型决定检索的那一刻，翻查题签上出现的是**模型真正用的检索词**；检索结果一回来（回答还没写完），金线就落到那些部门的楼上；最后回答到了，再变红、飞过去。流式出任何问题，自动退回原来的 `/api/v1/chat`，用户看不出差别。

**原理**：LangGraph 每个节点（prepare、model、tools、publish）结束时都能拿到这一步的结果。新接口把这些结果按「服务器推送事件」（SSE）的格式一条条写回给浏览器；前端边读边换算成 A5 的 `trace`。原来的 `/api/v1/chat` 一个字都不改。

**只许改**：`backend/app/agent/graph.py`、`backend/app/api/v1.py`、`frontend/src/api/client.ts`、`frontend/src/stores/chat.ts`、`src/stage/trace.ts`、`src/views/StageView.vue`；新建 `scripts/check_a6.py`、`tests/unit/sse.test.ts`、`tests/unit/trace-events.test.ts`、`tests/e2e/stage-stream.spec.ts`。

## 事件（契约，名字和字段照这个来）

每条事件的格式是 `event: <名字>\ndata: <一行 JSON>\n\n`。

| 事件 | 什么时候发 | `data` |
|---|---|---|
| `accepted` | 开始执行 | `{ "request_id", "trace_id" }` |
| `prepare` | prepare 节点结束 | `{ "normalized": 规范化后的问句, "identity": 身份或 null, "college": 学院名或 null, "year": 年份或 null, "notes": [校验提示] }` |
| `tool_call` | model 节点结束、并且模型要调工具 | `{ "n": 第几次模型调用, "calls": [{ "name": 工具名, "args": 参数 }] }` |
| `tool_result` | tools 节点结束 | `{ "results": [{ "name", "evidence": [{ "id", "issuer" }], "flow": { "id", "available" } 或 null }] }` |
| `final` | publish 节点结束 | 和 `/api/v1/chat` 返回的 `ChatResponse` 完全相同 |
| `error` | 开始流之后出了技术错误 | `{ "code", "message", "retryable" }` |

`final` 或 `error` 之后流结束。

## 要做的事

**后端**

1. **`graph.py`**：
   - `ChatState` 加 `prep: Dict[str, Any]` 和 `tool_log: List[Dict[str, Any]]`。
   - `node_prepare` 把上表 `prepare` 那几样存进 `state["prep"]`（`normalized` 用 `normalize_query` 返回的文字）。
   - `node_tools` 每调一个工具，往 `tool_log` 追加 `{ "name", "args", "evidence": [{ "id", "issuer" }], "flow": … }`（`issuer` 在检索工具的返回里已经有了），并把本次追加的这几条也放进返回值。
   - `run_turn` 加一个参数 `on_event=None`。有 LangGraph 时改成 `for update in _COMPILED.stream(state, stream_mode="updates")`：每个 `update` 是 `{节点名: 这个节点的返回}`，按节点名换算成上表的事件，调 `on_event(名字, data)`；`slots` 从 prepare 那一步取，`final` 从 publish 那一步取。退化路径（A0 改过的循环）在每个节点后面调同一个换算函数。`on_event` 为 `None` 时不调。**返回值和以前完全一样。**
2. **`v1.py`**：
   - 把 `chat()` 拆成两个函数，两个接口共用：`_begin_turn(req)` 做会话校验、幂等、选项回放、取历史（会抛 404、409、410、422 的都在这里），返回「已经有缓存的结果」或者「这一轮要用的输入」；`_persist_turn(...)` 就是现在写库的那几行。`chat()` 改成调用这两个，行为不变。
   - 新接口 `POST /api/v1/chat/stream`，请求体和 `/chat` 相同：
     - 先调 `_begin_turn`。抛错就照常返回错误（这时还没开始流）。有缓存：流里只发一条 `final`。
     - 否则：建一个 `asyncio.Queue`；用 `loop.run_in_executor(None, …)` 在线程里跑 `run_turn(…, on_event=…)`，`on_event` 用 `loop.call_soon_threadsafe(queue.put_nowait, (名字, data))` 把事件放进队列；`run_turn` 结束后**在同一个线程里** `_persist_turn`，再把 `final` 放进队列。线程里出异常：放一条 `error`。
     - 返回 `StreamingResponse(生成器, media_type="text/event-stream", headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})`；生成器先发 `accepted`，然后从队列里取一条发一条，发完 `final` 或 `error` 结束。
     - 同一个 `(session_id, request_id)` 正在跑时又来一次：返回 409，`code` 是 `request_inflight`（用一个进程内的集合记录正在跑的）。
     - 客户端中途断开：线程照常跑完并写库（这样用同一个 `request_id` 重试能直接拿到结果）。
   - 不要加 GZip 中间件。

**前端**

3. **`client.ts`**：新增 `api.streamChat(body, onEvent, signal): Promise<ChatResponse>`：`fetch` POST，`resp.body.getReader()` 加 `TextDecoder` 读；按空行（`\n\n`）切分事件，每条按 `event:`、`data:` 两行解析，调 `onEvent(名字, data)`；收到 `final` 时 resolve 它的 `data`；收到 `error` 或连接断开时 reject。**超时**：连续 `SHZU_STREAM_IDLE_MS`（默认 15000）毫秒没收到任何字节就中断。把切分事件的部分写成一个单独导出的纯函数 `parseSse(buffer: string): { events: {name, data}[]; rest: string }`，方便测试。
4. **`chat.ts`**：
   - 等待中的那一轮（`ChatTurn`）加一个字段 `progress: { name: string; data: unknown }[]`。
   - `_doRequest` 先用 `streamChat`，每收到一条事件就 push 进 `progress`；成功就和以前一样处理 `final`。
   - 流失败（任何原因，包括 404 说明后端还没这个接口）：用**同一个 `request_id`** 调原来的 `api.chat`。收到 409 且 `code` 是 `request_inflight`：等 1.5 秒再试，最多 3 次。
   - 网址带 `stream=0` 时不用流（测试和出问题时的开关）。
5. **`trace.ts`** 新增 `traceFromEvents(events, places, meta): Partial<Trace>`：
   - 没有事件：`phase: 'read'`。
   - 有 `prepare`：`phase: 'read'`，`query` 是 `normalized` 的前 10 个字。
   - 有 `tool_call`：`phase: 'search'`，`query` 是最后一个 `search_campus_knowledge` 调用的 `args.query`（没有就保持上一条）。
   - 有 `tool_result`：`phase: 'verify'`，`hits` 用所有 `tool_result` 里的 `evidence` 按 `issuer` 合成（规则同 `traceFromResponse`），`evidence` 是去重后的证据条数。
   - `live: true`。
6. **`StageView.vue`**：A5 的驱动里，等待中的那一轮有 `progress` 时，每次 `progress` 变化就 `setTrace(traceFromEvents(...))`（代替 A5 的 400 毫秒定时）；回答到了以后的流程和 A5 完全相同（`verify` 停留、变红、`showAnswer`）。流式时 `verify` 可能在回答到之前就开始了，这时回答到了直接停留 450 毫秒再进 `answer`。

## 验证

`scripts/check_a6.py`（不需要 API Key；假模型的做法同 `check_a0.py` 第 3 条）：

## 常见错误

- 在 `async def` 里直接调 `run_turn`：整个服务卡住，所有人都在等这一个请求。要放进线程。
- 流开始以后才发现会话不存在，想返回 404：来不及了，状态码已经发出去了。所有会抛错的检查都放在 `_begin_turn` 里，先做。
- 本地流得好好的，部署后一次性全到：中间的代理在攒包。看响应头那两项；Nginx 还要关 `proxy_buffering`。
- 前端用了 `EventSource`：它只能发 GET。用 `fetch` 读流。
