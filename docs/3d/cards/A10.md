# A10 提速（第二批）

**做完的样子**：盲测 50 题的平均耗时下降；服务刚启动后的第一题不再比后面的慢一截；前端不会在服务端还没放弃的时候先放弃；每次提问少一次多余的请求。页面上没有任何变化。

**原理**：见 `ALIVE.md` 第 6.2 节。有证据的问题至少两次串行调用模型；第一次调用知识库、索引和模型客户端都是现加载的；前端 20 秒超时，而服务端最坏要 24 秒。

**只许改**：`backend/app/main.py`、`backend/app/agent/deepseek_adapter.py`、`backend/app/agent/graph.py`、`backend/app/knowledge/retriever.py`（只为加一个「已加载」的标志）、`frontend/src/api/client.ts`、`frontend/src/stores/chat.ts`、`README.md`（只改写模型配置的那一段，第 24 行附近）；新建 `scripts/check_a10.py`、`scripts/time_model.py`；`tests/unit/chat-store.test.ts` 里追加。

## 要做的事

**再改**（每一项改完都能单独验证）：

3. **超时按实测定**：`DEEPSEEK_TIMEOUT` = 第 1 步 95 分位 × 1.5（向上取整，最少 5 秒）；`SHZU_TURN_BUDGET` = `DEEPSEEK_TIMEOUT` × 2 + 1；`max_retries` 改成 0（重试交给前端的「重试」按钮）。写进 `README.md` 模型配置那一段（写清楚比赛环境的 `.env` 该填什么），并注明是哪天量的。**前端**的聊天请求超时改成 `SHZU_TURN_BUDGET + 3` 秒：后端在 `/api/v1/health/ready` 的返回里加一个字段 `turn_budget_s`，前端启动时读它；读不到用 20 秒。
4. **预热**（`main.py`）：用 FastAPI 的 `lifespan`：启动时调一次 `get_kb()`、建好检索索引（调一次检索，查「图书馆」）、`jieba.initialize()`、`deepseek_adapter.create_chat_model()`。任何一步失败只打警告，不影响启动。
5. **模型客户端不过期**（`deepseek_adapter.py`）：去掉「300 秒重建一次」，只在配置（Key、模型名、地址）变了的时候重建。
6. **前端少一次请求**（`chat.ts` 的 `ensureSession`）：已经有 `sessionId` 时不再先调 `api.messages` 验证，直接返回；会话失效靠聊天接口返回的 404、410 来发现（`_doRequest` 里收到这两个状态时：建新会话，用新的会话号和**新的** `request_id` 重发一次，界面上提示「会话已过期，已为你新开一个」）。
7. **预取检索（有风险，最后做，评测说了算）**（`graph.py`）：环境变量 `SHZU_PREFETCH=1` 时，`node_prepare` 用规范化后的问句调一次 `search_campus_knowledge`，把结果作为一对「模型调了检索工具 + 工具返回」的消息放进 `messages`（工具调用的 id 写 `prefetch`），返回的证据 id 加进 `evidence_ids`。这样模型第一次调用时手里就有资料，多数问题不用再调工具。默认关。
   - 打开后跑一遍评测：**总分不降**并且耗时中位数下降，才在 `README.md` 里写明比赛环境把它设成 1；否则保持关，把两次的数字都记进 `PROGRESS.md`。

## 常见错误

- 超时设得太紧，盲测时一半的题报超时：超时要按第 1 步量出来的数定，不要照抄别人的数字。
- 预取以后模型在打招呼的回答里也引用证据：提示词里已经写了「纯对话不列 evidence_ids」，评测会发现；发现了就别打开预取。
- 去掉会话验证后，换了浏览器的用户一直报错：第 6 步里收到 404、410 要自动建新会话重发。
