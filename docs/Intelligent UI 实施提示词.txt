我想把「石大智多星」做成一个能在聊天里接着办事的校园助手

请在当前仓库直接做这次改动。项目叫「石大智多星」，前端是 Vue 3、TypeScript、Pinia、Vite，校园沙盘用了 Three.js。先看已有代码和 git status，从现在的版本接着做。我希望学生问完一句话，先看到这一轮最该做的事，然后能点进去补信息、核对材料、看依据、找楼或继续填表。聊天和校园沙盘都要能走这条线。比如「学生证丢了去哪补办」这一轮，地点、出发前要确认的事、可用的联系方式和定位入口应该放在一起，不必让学生先读完一大段说明再往下找。

先做第一阶段，跑通后再继续第二阶段。第三阶段作为后续扩展。每做完一个阶段，先用已有测试或一段明确的操作验证它。

一、先看这些地方

从项目根目录开始。接口及类型在 frontend/src/api/client.ts，聊天状态和请求在 frontend/src/stores/chat.ts。普通聊天看 frontend/src/views/ChatView.vue，沙盘聊天看 frontend/src/components/stage/AnswerPanel.vue 和 AskDock.vue。已有回复正文、动作和引用组件分别是 AnswerBlocks.vue、ActionCards.vue 和 EvidencePanel.vue。先读它们，再决定哪个组件需要拆小一点。办事向导看 WorkflowView.vue、stores/workflow.ts、stores/flowDraft.ts，已经有分步表单、预设确认、草稿恢复、预览和导出。服务目录看 ServicesView.vue。定位看 StageView.vue、stores/stage.ts、stage/places.ts、stage/packs.ts，以及 public/campus3d 里的校区资料。主题样式在 styles/theme.css、swiss.css 和 stage.css，已有日间、夜间、跟随系统。

所有场景的展示都从现有 API 取数据。ChatResponse 有 status、answer、clarify、citations、actions、workflow 和 unknown_fields。actions 中已有 checklist、repair、place、errand 四种数据。它们由后端场景工具返回。先写一层简单的前端展示逻辑，输入是当前轮次的响应，输出是本轮要显示的任务卡、建议动作和引用。比如可以用一个小的 TypeScript 函数加几个 computed。条件用接口字段判断，保留旧响应和缺字段时的正文路径。沿用现有接口、Pinia store、路由和主题变量。把你没写的工作区改动一起保留。

二、第一阶段，先把一轮回答变成能操作的结果

1. 普通聊天和沙盘都要看到下一步

普通聊天要在当前助手消息内展示下一步。沙盘在现有右侧回答面板里展示同样的动作，保留现有的收起、展开和输入。两个入口共享判断规则，布局可以不同。桌面把主要内容和出处分开，沙盘的紧凑卡片只放最重要的一两项，并有可点开的详情。每轮最多一个醒目的主按钮。正文和出处仍在这条消息里。老消息照常显示当时的结果，历史追问保持只读。

主动作按下面的条件来定。当前有明确追问时优先显示追问本身和选项。有现场办事单且地点可定位时，用「在沙盘查看」。有报修分诊时，优先让人看到自查步骤，有草稿才出现「复制报修草稿」。有材料清单和有效向导时，用「进入核对向导」。只有 workflow 状态时，沿用原来的向导入口。常规事实问答直接展示答案和引用。普通闲聊例如「你好」，就正常说话。组合响应里，现场办事单和地点卡指向同一栋楼时，主按钮出现一次，地点的细节仍然可以查看。

2. 把追问做成一张能回答的小卡

用 clarify.question 做标题。选项的文字用 label，提交用 choice.id，走 chat store 的 pickChoice。需要手动输入时用 input_hint 提示，实际发送走原来的输入框。点击后立即禁用当前追问按钮，避免连续点击重复发请求。只让当前会话中最后一条未回答的追问可操作。取消等待或失败后，把控制权交回用户。用户点重试时复用原 request_id，原请求是选项时保留原始 choice_id。等待结束只表示前端不再等待，迟到回复按原会话和请求标识处理。用键盘能点选，中文输入法选字期间按回车只确认候选词。可以用「宿舍网断了怎么办」和现有的追问测试走一遍。

3. 校园办事卡分四种，直接用现有字段

现场办事单 errand 先显示 building 和 room，再显示 dept、phone、hours 和 confirms。房间号用比正文更大的字，和楼名放在一起。缺哪一项就展示有意义的状态，例如「办公时间待向办公室确认」。materials_confirmed 为 false 时，把「先向办公室确认材料」放进出发前提醒。place.evidence_id 可点开出处，有有效 building_id 才出现可定位动作。用「学生证丢了去哪补办？」检验。真实房间和电话由这一次响应决定。

报修 repair 先放校区、楼栋和影响范围，再逐条显示 steps。保留 announcement 的实际状态。库内命中、官网未能连接、未找到覆盖当前地点的公告要能看出区别。只有 entry 里有相应资料才出现可拨电话或入口。复制成功后显示「已复制报修草稿」。复制失败时给一条可见提示，并保留可选中的草稿文本。草稿标为「未提交」。用「中区18号楼宿舍网络无法连接」检验。

材料核对 checklist 按后端给的四个状态显示。verified 显示「已有依据」，needs_user 显示「待你补充」，needs_college 显示「待学院确认」，needs_web 显示「待官网核实」。卡片顶部可以显示这些状态各有几项，计数用实际 items 数组。列表逐项显示 label、detail 和可点的引用。year 和 year_note 放在容易看到的地方。flow.historical 为 true 时，在点击向导前让学生看到「历史演示」，进入向导后仍有原来的年度提示及确认。用「今年国家励志奖学金怎么申请？」检验，展示当前响应核实到的内容以及缺项。

地点卡 place 显示 matches。有多个候选或 ambiguous 为 true 时，让学生点选候选楼，显示每项现有的校区信息。选中以后再聚焦对应 building_id。避免当前自动定位路径抢先把第一项标成唯一地点。检查 stage/places.ts 的 resolvePlace 和调用它的代码，地点有歧义时也要挡住正文关键词和发布单位的自动回退。明确的 errand 位置同样要以工具结果为准，判断歧义以本轮地点卡为线索。无登记楼号时仍展示文字地点。地图不可用时继续用已有静态降级，明确显示文字定位。楼栋的近看、切换校区和重置都沿用原来的沙盘方法。页面只显示有数据支持的地点信息。

4. 引用跟着具体内容走

普通聊天保留现有角标和 EvidencePanel，沙盘保留出处卡。材料项用 evidence_ids，地点可以用 evidence_id，正文用 citation_ids。对得上当前响应 citations 的 ID 再显示成可用入口。使用答案本轮的引用索引，重复出现的是同一个出处。点开后尽量看到标题、发布方、原文摘录和时间条件，完整来源沿用现有详情页。移动端优先在消息旁展开。快速切换两条引用时，最后选择的那条应与右侧原文相符。中途部分详情取不到，可以展示响应本来就带的摘录，并说明详情暂不可用。

5. 给等待、缺项和失败具体的反馈

当前接口是整包返回，等待时用「正在查询校内资料…」。取消和重试复用原入口。资料不足时先展示用户需要知道的缺项，从 unknown_fields 或后端 message 读取。存在 clarify.choices 才展示可以提交的选项。对未知类型或旧会话缺少 actions，正文和已有引用要照常显示。如果后端返回多个支持类型，保留用户可用的补充动作，避免多张同样占满屏幕的卡。模型不可用时显示本轮状态，以及可用的「重试」和「打开服务目录」。历史回合、取消后的迟到结果、其他会话的响应都不应改写当前轮的主动作。只有后端实际确认的状态才显示为完成。

三、第二阶段，在两个页面之间接住正在办的事

6. 把原来的「继续办理」入口带到沙盘和服务目录

普通版首页 HomeView 已经用 listDrafts() 显示最近草稿。复用这套来源，在沙盘非观景状态和服务目录也放一个小入口，最多显示最近两条适合继续的记录。有草稿才出现。只显示事项名、上次步骤和下一项要填的字段标签，点开走已有的 /workflows/:flowId?draft=<会话标识> 恢复路由。没有 nextTodo 时显示「查看上次进度」，已有模型推断信息继续走原有的预设确认。草稿记录没有校方办理完成标记，页面用「继续填写」「已导出文书」等与实际事件相符的表述。保留现有会话与事项的隔离规则，顶部卡片不展示姓名、联系电话、住址、排名值。修改表单后预览应失效，按原逻辑重新核对后再导出。

7. 给校园沙盘里的学院一个容易认出的入口

把已经准备好的院徽用在校园沙盘的学院列表。手头的文件位于项目同级的「石河子大学院徽」文件夹，修改前看一下实际有哪些可用图片。媒体文件按本项目部署规则放进 frontend/public 下一个明确的资源目录，维护一小份学院名到文件名的显式映射。当前沙盘列表用 campus.meta.json 的学院数据，学院名对照 data/workflows/colleges.json 及已有别名。像「文学艺术学院（新闻传播学院）」和「信息科学与技术学院（网络空间安全学院）」要匹配到对应的本地短名文件。列表里用小尺寸带留白的徽图和完整学院名，缺图时提供有统一尺寸的文字占位。用图片作识别辅助，图片缺失或加载失败时仍能读到学院名。保留原列表默认顺序和原有定位能力。点「在沙盘查看」继续走已登记楼栋的位置，地点待确认的学院仍按现有状态展示。可以加一个就在这一行的「问这个学院」按钮，将「我想了解<学院全名>的学院概况」带入现有问话流程，用户点击后才发出。

四、第三阶段可以扩展什么

可以增加「常用办事」快捷入口，让用户直接进入真实服务目录或已有向导。服务条目用 api.services() 或已有配置，过滤时使用实际 service_id、board、flow_id。固定示例可以来自现有 sample_questions。不要把传闻当成校园资料。也可以把学校办事地点多候选做成更容易比较的列表，横向对照校区、楼名、位置状态和出处，仍使用真实 matches。还可以增加「查看不同年份依据」的对照视图。在同一轮确实有两条以上带明确时间条件的引用时，才提供这个入口。并排或纵向显示原文的适用期、发布单位和摘录，沿用各自的引用编号和详情链接。学生仍能从每段原文看到它支持的内容。在前两阶段跑通前，先保留这些想法。

五、页面做成什么样

沿用项目的纸白、朱砂、墨蓝和细金线。使用现有主题变量，状态靠文字加颜色识别。标题用现有宋体标题变量，表单和正文按现有中文字体栈。视觉层级按「行动」「事实」「出处」排。一个需要点的主动作可以用朱砂实底，次级操作用细边框或文字按钮。正文用舒服的行高和可阅读的行宽，出处预览和补充详情可展开。沙盘高亮接着用原来的建筑轮廓、红色落点和引线。新 UI 的展开和收起做 160–220ms 左右的轻过渡，尊重 prefers-reduced-motion。用 1440、768、390 像素三种宽度看一遍。手机按单列排，常用按钮容易点，底部输入不盖住卡片和按钮。确保键盘焦点可见，折叠按钮标 aria-expanded，状态提示能读到，夜间主题也能看清小字。动效、图标和装饰都用来帮助看清当前状态或者下一步。

六、交付前这样检查

从 frontend 目录运行 npm run build、npm run test:unit 和 npm run check:bundle。端到端沿用 frontend/tests/e2e/fixtures/api.ts 的模拟接口。重点跑 flow-guide.spec.ts、stage-ask.spec.ts、stage-place.spec.ts、theme.spec.ts 及 baseline.spec.ts 里的相关用例。原有测试能覆盖的直接跑。新增行为缺少验证时，优先补「相同响应的聊天与沙盘动作一致」和「地点有歧义时不会自动选第一个」两条。接口模型可用时再手动跑一次真请求，与模拟验收分别记录。

最后至少实际走一遍这些例子。
- 学生证补办能看到地点、出发前确认，点后能定位，同一出处能打开。楼号缺失时看到文字地点。
- 奖学金卡能看出四种状态和涉及的年度，历史向导仍须原来的确认。
- 网络报修先追问位置或范围，再显示真实的自查步骤。复制出来的文本与草稿一致。
- 多候选地点点击第二项，定位到第二项。用已有测试夹具也可以。
- 普通问答和旧历史正常显示。快点两次选项只发一轮，失败可重试。键盘和中文输入可用。
- 从「继续办理」回到之前的步骤，手动内容仍在。编辑内容后旧预览失效。
- 手机没有横向溢出，夜间主题正常，静态沙盘也能打开地点信息，引用仍可点。
